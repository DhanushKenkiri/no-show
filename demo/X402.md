## What x402 is

HTTP 402 "Payment Required" as a real protocol. Flow:
1. Client requests a resource
2. Server responds 402 with a JSON payment requirement
3. Client signs a payment authorization **locally, with no transaction**
4. Client resends the request with the payment header
5. Server verifies via a facilitator, settles, and serves the resource

Monad Foundation joined the x402 Foundation (governed under the Linux Foundation
alongside Cloudflare, Visa, Mastercard, Google, AWS) and runs a live facilitator.

## Versions — READ THIS

- Versions 2.9.0–2.11.0 include the upto module but reference a proxy address
  that is NOT deployed on Monad (0x402039b3d6E6BEC5A02c2C9fd937ac17A6940002).

## Testnet USDC needs a custom money parser

Mainnet USDC resolves from the SDK's built-in asset table on >= 2.22.0.
**Testnet USDC does NOT** — you must register a money parser:

```ts
const monadScheme = new ExactEvmScheme();
monadScheme.registerMoneyParser(async (amount: number, network: string) => {
  if (network === "eip155:10143") {
    return {
      amount: Math.floor(amount * 1_000_000).toString(), // USDC = 6 decimals
      asset: "0x534b2f3A21130d7a60830c2Df862319e593943A3",
      extra: { name: "USDC", version: "2" },   // EIP-712 domain: "USDC", NOT "USD Coin"
    };
  }
  return null;
});
server.register("eip155:10143", monadScheme);
```

## Schemes

| Scheme            | Use for                          | Mechanism |
|-------------------|----------------------------------|-----------|
| `v2-eip155-exact` | fixed price (DEFAULT — use this) | EIP-3009 `transferWithAuthorization`, or Permit2-proxy fallback |
| `v2-eip155-upto`  | variable / metered amounts       | Permit2 only. Client signs a max, facilitator settles for actual <= max. **Supports $0 settlement with NO on-chain transaction.** |

Use `exact` for the buy flow. `upto` is only for the borrow/deposit flow and is
a stretch goal — it additionally requires a Permit2 allowance for the proxy and
an `extra.facilitatorAddress` bound into the Permit2 witness.

## Security properties to rely on (and to state in the README)

- The authorization cryptographically **binds the recipient address**. The server
  or facilitator CANNOT redirect funds to a different address than the client
  signed.
- Each authorization has `validAfter` and `validBefore`. **`validBefore` is our
  timeout — an unreleased authorization simply expires. There is no refund
  transaction because the money never moved.**
- Permit2 nonces provide replay protection; each authorization settles once.

## Status codes

- `402` — payment required (normal, this is the protocol working)
- `412 PRECONDITION_FAILED` — Permit2 allowance for the proxy is insufficient.
  Client must approve and retry. Only occurs on the `upto` scheme.
